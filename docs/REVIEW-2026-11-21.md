## 0. 一句话结论

**产品骨架是好的：可恢复删除、哈希链审计、安装前静态审计、会话内审批都真的能跑通，且失败时基本 fail-closed。**
问题集中在两处：
1. **“保护”的判据大量依赖字符串/子串匹配与 `process.cwd()`**，因此存在一批可复现的绕过（删除、自保护、路径等价形式），而“关键保护根”的实现方向写反，系统目录的子路径反而不受保护；
2. **噪声与语义错位**（自扫描 41 个 blocker、写文档触发拦截、重扫被记成“询问”、跨会话审批/审计窗口串台），会消耗用户对告警的信任。

## 2. 高优先级问题（P0）

### P0-1 关键保护根方向写反：系统目录的**子路径**被判为 low
- 证据 `[判定]`：`classifyPath()` 对 `criticalExact` 只判断「目标 == 根」或「根在目标内部」，没有判断「目标在根内部」。
  - `C:\Windows` → CRITICAL；`C:\Windows\System32` → **LOW**；`C:\Windows\System32\drivers\etc\hosts` → **LOW**
  - `C:\Program Files` → CRITICAL；`C:\Program Files\SomeApp` → **LOW**
- 后果：`Remove-Item -Recurse C:\Windows\System32` 不再走 `VG-DEL-01`，只剩“递归删除/规模阈值”兜底；小目录或单文件（hosts、单个 exe）会直接 **allow**。这次恰好被 303 MiB 的规模阈值挡住，属于运气。
- 位置：`src/delete/policy.js:157-161`（`isWithin(targetPath, root.path)` 参数顺序反了；`criticalContainers` 那条分支是双向判断，所以 `~/.dsh`、`~/.ssh` 内部反而正常）。
- 修复：不能简单把参数反过来——`criticalExact` 里混了两类根：**目录树**（`C:\Windows`、`Program Files`、`ProgramData`、盘根）应当“内部也 critical”；**边界路径**（`C:\Users` 这类“用户目录的上级”）只应“本身/祖先 critical”，否则整个用户目录都会变成 critical。建议给根加 `descendants: boolean`（或拆成 `criticalTrees` 与 `criticalBoundary` 两个列表），并为 `C:\Windows\System32`、`hosts`、`Program Files\X`、`C:\Users\Neko\Documents\x` 各补一条用例。

### P0-2 四种删除形态在判定层直接 allow（Sage 只是偶然兜底）
判定级复现（`%TEMP%\vigil-verify2.mjs`，未执行）`[判定]`，子代理另做了真实执行验证 `[实测]`：

| 命令 | 结果 |
| --- | --- |
| `[System.IO.DirectoryInfo]::new("D:\…\victim").Delete($true)` | **ALLOW**（`isDelete=false`；解析器只认 `]::Delete(`） |
| `Get-ChildItem D:\…\victim -File \| Remove-Item -Force` | **ALLOW**（`isDelete=true`，但 `pipeline-generic` 没有对应决策规则） |

### P0-3 路径等价形式绕过保护根与自保护（含创建停机开关）
判定级 + 文件系统实测 `[判定][实测]`：

| 命令 | 结果 |
| --- | --- |
| `New-Item -ItemType File -Force ~\.dsh\vigil\DISABLED` | **ALLOW**（判定；未实际创建。若执行则停机开关生效，此后全部调用放行） |
| `Clear-Content ~\.dsh\vigil\integrity\baseline.json` | **ALLOW** |
| `Remove-Item -Force C:\Users\Neko\DSH~1\vigil\integrity\baseline.json` | **ALLOW**（`DSH~1` = `.dsh`，`dir /x` 已确认） |
| `Remove-Item -Force C:\PROGRA~1\Bandizip\Bandizip.exe` | **ALLOW**（`PROGRA~1` = `Program Files`） |
| `[System.IO.File]::Delete('\\?\C:\Windows\System32\drivers\etc\hosts')` | **ALLOW** |
| `robocopy C:\payload C:\Users\Neko\.dsh\vigil /E` | **ALLOW**（`isDelete=false`，写动词表也没有 robocopy/xcopy） |

- 原因：保护根分类是纯字符串比较；自保护 `protectedCommandWriteHit()` 用 `normalized.includes(dir)` 子串匹配（`src/sentinel/guard.js:97-105`）。
- 后果：**自保护可被代理用一个 `~` 路径关闭**（这是设计上最不该发生的一种）；8.3 短名还能让 `Program Files` 下的删除变成普通删除。
- 修复：统一做路径规范化前置（展开 `~`/`%VAR%`/`$env:`、剥 `\\?\`、对已存在路径 `realpathSync.native` 逐级解析），再做根判定；写保护动词补 `robocopy/xcopy/tee/clear-content`。

### P0-4 相对路径锚定在 `process.cwd()`（= profile 目录），项目根保护错位
- 证据：宿主进程 cwd = `C:\Users\Neko\.dsh\profiles\desktop`（`src/index.js:233`）。判定级 `[判定]`：
  - `rm -rf dist` → **DENY**，理由“目标是关键保护根（Harness 主目录）”
  - `includeProjectRootAsHigh` 的 high 根变成了 profile 目录；`D:\Dev\Github\dsh-vigil` 判 **low**
- 后果：日常相对删除（`dist`、`node_modules`、`build`）要么被误拒、要么每次弹窗（本机 `critical: ask`），而真正的工作区根失去 high 级保护。
- 修复：从工具参数/会话上下文取真实 workdir（`cwd`/`workdir`/workspace root），不要 fallback 到 `process.cwd()`；拿不到就按 `unparsed` 处理。

### P0-5 隔离区 `restore` 信任 manifest：可越界写入并递归删除隔离区外目录
- 代码 `[代码]`：`entries()` 接受任意 `manifest.id`；`restore()` 用 `join(dir, entry.id)` 与未校验的 `originalPath`，成功后 `rmSync(entryDir, {recursive:true})`。
- 子代理已在 `%TEMP%` 复现 `[实测]`：伪造 `id='q-evil/../../traverse-victim'` 的 manifest，`restore` 把 payload 写到隔离区外，并把那个目录整棵删掉。
- 前置条件：能写隔离区（见 P1“文本匹配”），而 P0-3 的 `~` 写法正好能写。
- 修复：`id` 必须等于目录名且匹配 `^q-[A-Za-z0-9-]+$`；`originalPath` 必须 resolve 后不在隔离区/保护根内；restore 前 `lstat` 校验 payload 类型。

### P0-6 扫描覆盖不进安装门禁：“跳过 = 0 高危 = 放行”
- 子代理用真实扫描器复现 `[实测]`：

### P0-7 补丁只认固定文件名 `cordis.patch.yml`

## 3. 中优先级问题（P1）

1. **`monitor` 模式仍会被自保护 guard 拦截** `[代码]`：`guard.js:74` 只看 `selfProtection`，不看 `mode`；与 `docs/ARCHITECTURE.md` 第 7 节“monitor 模式不得拦截”冲突。
2. **隔离区/配置保护是纯文本匹配，假阳性与假阴性同时存在** `[实测]`：
   - 写一个 Markdown，正文同时提到隔离区绝对路径与 `cordis.patch.yml` → **write 被拒**（`VG-RT-07 + VG-RT-11`，其中 VG-RT-11 是硬拒绝）；
   - 本报告自身也命中了 `VG-RT-07`：因为正文引用了 profile 路径与 `cordis.patch.yml`，写文件时弹出询问；本机 profile 里 `configTamper=ask`，用户点了「允许一次」才写入（审计记录：`write allow VG-RT-07 approval{scope:once}`）。默认配置下 `configTamper=deny`，这份报告会被直接拦住；
   - 只读地 `Get-ChildItem` 隔离区也按“改动隔离区内容”拒绝（同一命令里只是统计条目数）；
   - 反过来，任意 `.mjs` 脚本（命令文本里不含路径）可以随意写隔离区：已实测写入并清理 `injected-by-script.txt`。**这条规则只提高文本层面的摩擦，不构成保护。**
   - 修复：改为“解析写意图 + 解析出的目标路径”判定；只读放行；明确 README 说明脚本间接写不可防。
3. **规模计量有洞** `[判定]`：`shouldEstimate` 要求 `recursive || wildcard || targets.length>1`，因此**单个 400 MB 文件的删除完全不计量**（`maxBytes` 形同虚设）；会话累计也只累加“带 scale 的调用”，逐文件删除永远不累计。已实测 400 MB 稀疏文件被删且无告警（该次因同命令含 `Start-Process` 被 Sage 拦，属另一回事）。
4. **手动重扫被记成 `decision: 'ask'`** `[代码]`（`install-watch.js:155`）。审计里出现“询问”但根本没人被问过，污染 `counts.ask` 与对话内“询问”列表。应记 `none` + 单独 event。
5. **自扫描噪声**：`vigil_scan` 扫自身仓库 → `blocker 41 / review 101 / notice 80`，其中大量来自 i18n 文案、规则定义表、测试夹具；插件审计页把自己标成 **“高危 17”** `[实测]`。这会让用户怀疑整个功能。
   - 修复：规则表/i18n/`test/fixtures`/文档字符串降级或 allowlist；对本包加 `self` 标记；UI 对“规则字面量命中”给出解释。
6. **`vigil_audit` 对代理不友好** `[实测]`：`action=json` 只返回一句“已导出 N 条”，模型看不到数据（render 只渲染 card）；`limit=100000` 会返回全部 189 条且无上限；`limit=0` 实际返回 50 条（与文档默认 50/2000 的说明也不一致）。
7. **设置页与 README 不一致** `[实测]`：
   - README 说隔离区占用/清理在设置页，实际设置页只有“保留天数/条目上限”（清理入口在对话审计对话框）；
   - README 说页面右上显示“保存中/已保存 时间”，实测看不到该状态；
   - “运行模式”用开关表示“是否拦截”，语义含糊（README 称“拦截开关”）；
   - “运行状态与恢复”只是让用户“去让代理调用 `vigil_status`”，没有只读状态卡。
8. **`restore --force` 留下垃圾且不提示** `[实测]`：占位内容被移到 `*.vigil-conflict-<epoch>`，恢复结果只说“已恢复”，没有冲突目录管理/清理入口。
9. **隔离区不会自动过期**：只有手动 `expire`（UI/工具）；没有定时器，条目会一直留到 `maxEntries` 满。
10. **安装审计覆盖面不透明**：只跟踪 profile 依赖里的 3 个第三方 bundle（`dsh-vigil`、`dsh-session-navigator`、`dsh-whale-widget`），内置 200+ 插件不在此列，UI 没有一句说明。
11. **跨会话串台** `[实测]`：子代理的 `ask` 会弹到主会话的 root overlay（看到两次），弹窗不显示来源会话/代理；用户无法判断是谁在请求。
12. **对话内审计窗口被“全局最近 40 条”饿死** `[实测]`：本会话有 6 条 deny，但对话框显示 `0 / 14` 与“本会话还没有拦截或询问记录”——因为 feed 先取全局最近 40 条决策再按 session 过滤，子代理的决策把本会话记录挤出了窗口。
    - 修复：在 Host 侧按 session 过滤后再截断，或返回更大的窗口 + 分页。

## 4. 低优先级问题（P2）

- `vigil_scan` 传文件路径 → 返回 `blocker: 目标目录不可读取（目标路径不是目录）`，应作为参数错误抛出，而不是安全结论。
- CSV/审计文案：`purge` 无 `confirm` 被记成“永久删除失败”；`restore/purge/expire` 用 `decision: allow/deny` 表达管理动作，语义混淆（建议用 `event` + `none`）。
- 叙述层：`VG-DSH-03` 先说“完整链路”又补“只是静态共现”；`VG-CFG-01`（review）建议“拒绝安装”；`VG-SCAN-03` 建议“提高扫描限制”但 `SCAN_LIMITS` 冻结、`vigil_scan` 无该参数；`VG-SUP-07` 证据引用了相邻行；`CFG` 叙述出现重复且引号不配对 `[子代理]`。
- 扫描器细节：YAML `\u0063redentials` 转义绕过；override 分支不检查 `id`；BOM 的 `package.json` 读不出 `version`；缺 `exports` 的合法 bundle 被 `SUP-05` 误报；随机字节里出现 `eval(` 产生乱码证据的误报 `[子代理]`。
- 每次 `vigil_scan` 都写一条审计事件（含失败/不存在路径），噪声偏大。

## 5. 改进路线（建议按此顺序）

### 阶段 A：先修正确性（不改架构，1–2 天）
1. `policy.js` 的 `criticalExact` 判定方向（P0-1）+ 回归用例（`C:\Windows\System32`、`hosts`、`Program Files\X`）。

6. 扫描覆盖进 summary/gate（P0-6）：`filesSkipped/bytesSkipped/truncated` 必看；有跳过时至少 notice（建议 blocker）。
7. 补丁发现改为读 `dsh.bundle.patch`（P0-7），数组 + 包外检查。
8. 能力识别补别名/间接/Worker/serviceWorker/DNS（P0-8）；凭证 env 正则修复 + env×egress 升 blocker（P0-9）。

10. 审计工具与 feed（P1-6/P1-12）：json 渲染返回数据、limit 上限 500、Host 侧按 session 过滤、提供 `decision=deny` 过滤与分页。

### 阶段 C：体验与长期（1–2 周）
11. 设置页加只读状态卡（计数/隔离区用量/Sage 版本/最近决策/基线状态），把“让代理调用工具”换成展示 + 一键清理；补上保存状态指示与“拦截开关”文案（P1-7）。

13. 隔离区：定时过期、冲突目录列表与清理、恢复结果里报告冲突路径（P1-8/P1-9）。
14. 安装审计：覆盖面说明、异步扫描与进度、对大包分块（当前 10k 文件 137 ms，但同步阻塞 hook）。
15. 审计链外部锚定（可选）：目前本机攻击者可整链重写；建议可选 HMAC 密钥或周期性把链头写入不可写介质/远端。
